# Jobs: rclone performance tuning

Detail for rclone performance settings and per-job overrides.

**rclone performance** (`utils/rclone_tuning.py`, README "Performance tuning"; stdlib only). Installation defaults `MOTUZ_RCLONE_{TRANSFERS,CHECKERS,MULTI_THREAD_STREAMS,MULTI_THREAD_CUTOFF,BUFFER_SIZE,S3_UPLOAD_CONCURRENCY,S3_CHUNK_SIZE,AZUREBLOB_UPLOAD_CONCURRENCY,AZUREBLOB_CHUNK_SIZE}` (unset/empty = `MOTUZ_DEFAULTS` for transfers/checkers, 16/32, lowered to the caps and dropped by `_add_motuz_defaults` if they would exceed the memory budget; rclone's default = no flag for the rest), caps `MOTUZ_RCLONE_MAX_{TRANSFERS,CHECKERS,MULTI_THREAD_STREAMS,UPLOAD_CONCURRENCY}` (64/128/32/64), `MOTUZ_RCLONE_MEMORY_BUDGET` (8G) and `MOTUZ_RCLONE_EXTRA_FLAGS` (only the flags in `EXTRA_FLAGS`, each with a validated value; no free-form flags); passed to app and celery via the `&rclone-environment` anchor in `docker-compose.yml`. `config.py` calls `rclone_tuning.settings()` at import, so an invalid value stops the app and the worker with a `TuningConfigError` naming the variable. Jobs store validated overrides in `copy_job.performance` / `hashsum_job.performance` (JSON; hashsum only `checkers`); names outside `PER_JOB` (e.g. `buffer_size`), non-integer / non-size values, values above a cap and combinations whose `estimate_memory` (`transfers × (max(1, streams) × buffer + max(upload_concurrency, streams) × chunk)`, chunk term for S3/Azure destinations only) exceeds the budget are a 400; settings for another backend than the destination's are dropped. `copy_flags` / `hashsum_flags` re-validate stored values against the current caps and emit one argv item per flag (`--transfers=32`) formatted from parsed numbers, inserted before `copyto` / `md5sum`; never build these flags from user text. `GET /api/copy-jobs/performance/?dst_cloud_id=` (`describe`) returns the fields for the destination's type, limits, defaults, `buffer_size`, the budget and the presets (`PRESETS`: Default, Many small files, Few large files, Maximum, clamped to the caps and reduced by `fit_preset` until they fit the budget). Frontend: `CopyJobPerformance.jsx` (collapsed section in `NewCopyJobDialog`), helpers with node tests in `utils/copyPerformance.js` (validation, the same estimate, preset matching); `createCopyJob` keeps the dialog open on failure and the dialog shows the error (`CREATE_COPY_JOB_FAILURE` is not in `alertReducer`); `EditCopyJobDialog` shows the settings, Retry keeps them, Check Integrity passes `checkers`. The e2e stack sets `MOTUZ_RCLONE_CHECKERS=16` and `MOTUZ_RCLONE_MAX_TRANSFERS=48` (`test/e2e/compose.yml`).

**S3 integrity and CPU (measured 2026-10-17, AWS us-west-2, 100 MB files):** Motuz passes `--s3-disable-checksum`, so multipart uploads (files >= `--s3-upload-cutoff`, rclone default 200 MiB) get no stored MD5: rclone's post-copy check logs `Dst hash empty - aborting Src hash check`, and Check Integrity (`rclone md5sum` on S3) sees empty hashes for those objects. Single PUTs are checked (ETag = MD5). Every request still carries `Content-MD5` (per part for multipart) and the SDK's CRC32, which S3 verifies (`BadDigest`). About two thirds of rclone's upload CPU is MD5 (single PUTs hash each file twice: a pre-read for `Content-MD5`, then during the transfer); TLS is about 5%. Multipart from 32M with `--ignore-checksum` doubled throughput (1.1 -> 2.1 GB/s on 8 vCPUs); `--ignore-checksum` is global in rclone and not in `EXTRA_FLAGS`, and only safe for S3 destinations that verify `Content-MD5` (AWS, Ceph RGW, MinIO), never for local/Azure/SFTP/Drive destinations.
