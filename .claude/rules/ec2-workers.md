# Temporary EC2 workers

Detail for temporary EC2 workers (off unless `MOTUZ_EC2_WORKERS=true`). Builds on remote-workers.md.

Off unless `MOTUZ_EC2_WORKERS=true` (README "Temporary EC2 workers" for operators, `deployment/aws/README.md` for IAM and launch templates). Every job queued for `MOTUZ_EC2_POOL` (`aws`, must equal `MOTUZ_LARGE_JOB_POOL`) gets its own instance that runs `motuz_worker.py --bootstrap-token-file ... --once` and terminates.
- **Settings** `utils/ec2_config.py` (stdlib only, `Config.EC2`, validated at import like `rclone_tuning`: `Ec2ConfigError` names the variable; refuses `MOTUZ_LOCAL_JOB_POOL` = the EC2 pool, and needs `MOTUZ_AWS_REGION`, `MOTUZ_PUBLIC_URL`, a source ref). `MOTUZ_EC2_INSTANCE_TYPES` (`1T:c7gn.large,10T:c7gn.2xlarge,*:c7gn.4xlarge`, decimal sizes, `architecture()` picks the arm64/amd64 template), `MAX_WORKERS` 2, `MAX_RUNTIME` 24h, `BOOT_TIMEOUT` 20m (bootstrap token TTL and claim deadline), `REAP_INTERVAL` 60s, `HALT_DELAY`, `MOTUZ_WORKER_SOURCE[_REF]` (default github.com/dirkpetersen/motuz at `MOTUZ_SOURCE_COMMIT`, which `bin/prod/build.sh` bakes into the image). The pinned rclone version/SHA256 are repeated in `ec2_config` (a test compares them with the Dockerfile).
- **Routing**: `job_routing.route` sends a large job to the EC2 pool only if both connections pass `ec2_eligible` (s3 with no endpoint or https on 443, azureblob, google cloud storage, dropbox, onedrive, drive; never `subtype='profile'`), else `central`; the size goes into `remote_job.source_bytes/source_files` (NULL = listing timed out = largest type). Migration `e4b8c2d6f1a3` (`ec2_worker`, those columns).
- **Launcher** `managers/ec2_launcher.py` (boto3, default credential chain; the module sets boto loggers to INFO because the root logger is DEBUG and botocore would log the user data): `worker_manager.queue_job` calls `job_queued` -> Celery task `ec2_dispatch`; `dispatch()` (under a PostgreSQL advisory lock) launches while `_active_count` (rows `launching/pending/running/stopping/stopped` plus alive tagged instances without a row) < max. One `ec2_worker` row per attempt (unique `job_type, job_id, attempt`, inserted before the AWS call). `launch_params` is exactly the IAM contract: `LaunchTemplate` (id if `lt-...`, else name; `Version`), `InstanceType`, `MinCount=MaxCount=1`, `ClientToken` `motuz-<installation id from SECRET_KEY>-<type>-<id>-<attempt>`, `UserData`, `TagSpecifications` (instance + volume: Project, Component, ManagedBy, Name `motuz-worker-copy-12`, MotuzJob `copy-12`), optional `SubnetId`; never ImageId/SecurityGroupIds/IamInstanceProfile/KeyName/MetadataOptions/BlockDeviceMappings/InstanceInitiatedShutdownBehavior (test compares with `central-launch-workers-policy.json`). `IdempotentParameterMismatch` -> adopt the instance found by the `client-token` filter; capacity errors (`InsufficientInstanceCapacity`, `Unsupported`, ...) -> `fallback_instance_type` once (attempt 2); transient errors leave the row `launching` for the reaper (retries after 2 min with the same ClientToken, fails after the boot timeout); others fail the job.
- **Reaper** `reap()` (`manage.py ec2 reap --loop`, started in the background by `celery-entrypoint.sh` when enabled; not Celery beat, because copy tasks occupy the worker processes for hours): refreshes row states from `DescribeInstances` (tag filters), terminates workers whose job ended, past max runtime (job failed), unclaimed after the boot timeout, stopped, and tagged instances without a row older than 10 minutes (one Motuz per account+region); fails jobs whose instance ended (`worker_manager.fail_remote_job`, reason plus the `get-console-output` command), relaunches once after `Server.InsufficientInstanceCapacity`, expires unused bootstrap tokens (`worker_manager.expire_bootstrap_token`), then `dispatch()`. `manage.py ec2 status|check` (check = DryRun RunInstances per type).
- **User data** `api/templates/ec2/worker-user-data.sh` (`build_user_data`: `@@NAME@@` placeholders shell-quoted, the token only in a quoted here-document, < 16 KB, no `set -x`): IMDS for root only first (nft `meta skuid != 0 reject`, else iptables owner match, else `dnf install nftables`: the AL2027 preview has neither, Ubuntu 26.04 ships iptables/nft already; verified with curl as `motuzjob`), `shutdown -h +<max runtime + 15 min>`, accounts `motuz` / `motuzjob` (sudoers: `motuz` may run only `/usr/local/bin/rclone` as `motuzjob`, SETENV), rclone with SHA256 (unzipped with python3), Motuz from the GitHub archive (pax header commit checked) or git, version check, token file 0400, `systemd-run` of a wrapper that runs the worker with `MOTUZ_WORKER_RUN_AS=motuzjob` and shuts down afterwards. Skips downloads when rclone/`/opt/motuz/.motuz-source` already match (hook for an AMI or the AL2027 installer).
- **Worker agent**: `MOTUZ_WORKER_RUN_AS` runs rclone as that account instead of the owner and fails jobs with a local side or a `profile_connection`; `--once` gives up (exit 3) after `MOTUZ_WORKER_ONCE_WAIT` without a claim, also while retrying an unreachable server (`Worker.gave_up`, via the `stop` of `Central.call`).
- **API/UI**: job DTOs have `pool` and `pool_status` (`worker_manager.annotate_location`: `central`/None, "running on w1", "waiting for a free EC2 worker slot", "starting worker (c7gn.large)", "running on c7gn.2xlarge"); `utils/jobLocation.js` (node test) shows them in the job tables and dialogs.
- Tests: `test/backend/test_ec2_launcher.py` (botocore `Stubber`: params, idempotency, limits, reaper decisions, capacity fallback, user data, no token in logs, settings, routing). The e2e `worker` suite checks the launcher-disabled state.
