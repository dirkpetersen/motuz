# File viewers (pager, images, Markdown, documents)

Detail for the read-only viewers. Summary and invariants are in CLAUDE.md.

- **Read-only viewer, a pager like `less`** (double-click on a file in a pane opens `FileViewerDialog.jsx`, which renders text, never HTML). `POST /api/system/files/view/chunk/ {connection_id, path, offset | before | from_end, length, follow}` → `{path, content, offset, end, size, bof, eof, encoding}` (`offset`/`end`: the byte range the content covers). `length` defaults to and is capped at 256 KiB (`utils/file_view.py`: `CHUNK_BYTES`; min 256); `offset` reads forward, `before` reads the chunk that ends there (the previous one), `from_end` the tail; only one of them, ints (not bools) validated in `parse_chunk_request` (400; an offset past the end is 400 too). A forward read at `offset == size` returns empty content with `eof` and reads nothing (the local reader skips both reads when the start is at the end; for cloud files `lsjson --stat` is the only rclone call). `follow: true` (only with `offset`; `ChunkRequest.follow`) is the viewer's follow mode: an incomplete last line is withheld until its newline arrives (`align_complete_lines`; `eof` is then true with `end < size`), an offset past the end returns no content and the new, smaller `size` instead of 400 (the viewer reloads the tail), and a cloud read past offset 0 skips the second `rclone cat --count 8192` (`skips_text_check`: the text check ran when the file was opened; the tail reload after a truncation checks again). Chunks hold whole lines (`align_forward` / `align_backward`, pure functions): forward reads end after the last `\n` unless at EOF, backward reads start after the first `\n` unless at BOF (reading one byte before the range, so a chunk that starts at a line keeps it); a line longer than a chunk is split, never inside a UTF-8 character. Text or binary is decided on the file's first 8 KiB (`HEAD_CHECK_BYTES`, `decode_text`) for every chunk, so the tail of a binary file is also 415; chunks decode with U+FFFD replacements. The older `POST /api/system/files/view/` (first 1 MiB, `{path, content, truncated, size, encoding}`) is kept. Local files are read as the user by `_VIEW_READER` (`sudo -n -u <user> -- env python3 -I -S -c`, absolute paths only, stat + fstat: regular files only, so devices and FIFOs are never read, non-blocking open, `pread` of the first bytes and of the range, a negative start counts from the end, returns size and start, so a tail is one process; timeout, process group killed on timeout); cloud files with `rclone lsjson --stat` (size; a folder is refused: `rclone cat` of a folder would print every file in it; bucket storage reports a missing path as a virtual folder, hence "is a folder or does not exist"), `rclone cat --offset --count` and, unless the range starts at 0, `rclone cat --count 8192` for the text check, as the user with `_formatCredentials`; the connection goes through `cloud_connection_manager.retrieve` (404 for other users'). Errors: 403 cannot read, 404 missing, 415 not text, 400 folder / not a regular file / relative path / bad offset or length, 504 timeout. Never log file contents. The dialog keeps the chunks itself (`utils/viewerChunks.js`, contiguous window of at most `MAX_CHUNKS` = 16 chunks = 4 MiB of text, chunks dropped at the far end and fetched again), loads the next/previous chunk when the viewport is within two screens of the loaded part's bottom/top, keeps the top visible chunk in place when chunks are added or dropped above (`getSnapshotBeforeUpdate`, `overflow-anchor: none`), focuses the scroll container (PageUp/PageDown, arrows, Space, Home/End of the loaded part), and has "Jump to top" / "Jump to bottom" (Ctrl+Home / Ctrl+End), which replace the window with the first chunk or the tail. **Follow** (button next to them, or `F`, like `less +F` / `tail -f`) goes to the end and polls `{offset: followEnd, follow: true}` (`utils/viewerFollow.js`, pure functions with node tests): 2 s for local files, 10 s for cloud connections, ×1.5 per poll without news up to 30 s, reset by new data; `setTimeout` after each answer, and every read of the dialog goes through one promise queue (`request()`), so no two requests overlap. New lines are merged into the last chunk while it stays ≤ 256 KiB (`appendFollowChunk`, so polls do not use up `MAX_CHUNKS`) and scrolled into view; the toolbar shows "Following… (updated 3 s ago)". Scrolling up by more than 16 px (wheel, PageUp/Home/↑, Jump to top) pauses the auto-scroll; lines are still appended (old chunks dropped at the top, the visible chunk kept in place) or, when the window no longer reaches the end, only counted: "Paused: N new lines below · Resume"; Resume or scrolling back to the bottom continues. `size < followEnd` → notice "File was truncated, showing the new end" and the tail is reloaded; 404 → notice, follow stops; 400/403/415 stop it too, other errors back off. More than 4 MiB new at once loads the tail instead. Polling stops when the dialog closes (unmount), while `document.hidden` (one poll at once on `visibilitychange` back), and after an hour without activity (keys, mouse, wheel) with a notice. Not detected: a file replaced by a different one that is already at least as long as what the viewer has.

- **Image and Markdown viewer.** Double-click dispatches by extension (`utils/viewerKind.js`, case-insensitive, node tests; `Dialogs.jsx` picks the dialog): `.png .jpg .jpeg .gif .webp .heic .heif .avif` → `ImageViewerDialog.jsx`, `.md .markdown` → `MarkdownViewerDialog.jsx`, everything else (SVG too) → the pager. `POST /api/system/files/view/image/ {connection_id, path}` (`utils/image_view.py`) returns the raw bytes: the type from the magic number only (`detect_type`: PNG, JPEG, GIF, WebP by their own signatures, HEIC/HEIF/AVIF from an ISO-BMFF `ftyp` box's major and compatible brands — `heic/heix/heim/heis/hevc/hevx` → HEIC, `mif1/msf1` → HEIF, `avif/avis` → AVIF; never the name or rclone's `MimeType`), anything else 415 (`NotAnImageError`, SVG with its own message: SVG can carry script), 413 above `VIEW_IMAGE_MAX_BYTES` (`MOTUZ_VIEW_IMAGE_MAX_BYTES`, default 25M, 1K..256M, parsed in `config.py` at import like the rclone settings; `&viewer-environment`, app only; the e2e stack uses 2M). Local: the same `_VIEW_READER` with a `max_size` argument (refused on fstat before reading anything, `{"error": "large", "size"}`), reading at most cap+1 bytes; cloud: `lsjson --stat` (413 before any `cat`) then `rclone cat --count cap+1`; both re-check what was read (the file may have grown). Headers (`response_headers`): the detected type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: no-store`, `Cross-Origin-Resource-Policy: same-origin`, `Content-Disposition: inline` with a sanitized ASCII name plus `filename*` (`safe_filename`). Same permission model and errors as the pager (403/404/400/504, other users' connections 404). The frontend fetches with the Bearer token (`apiActions.viewImage`, RSAA whose success payload is `{blob, type, size}`), never puts a token in a URL; fit to window by default, click / button / `Z` toggles 100%. Every fetched blob is checked with `decodeCheck` (`createImageBitmap`, or `Image().decode()`; 15 s timeout) before it is shown; PNG/JPEG/GIF/WebP always decode and AVIF (AV1) in every current major browser. **HEIC/HEIF** (HEVC): Safari decodes it itself; any other browser gets a JPEG converted on the server: the frontend decodes a tiny embedded HEIC picture once per page (`utils/heicProbe.js`) and `utils/heifConvert.js` (node tests) asks for the plain image only where that works, else for `convert: "jpeg"` at once (a corrupt file of the user says nothing about the browser; a plain HEIC that fails to decode is fetched again converted; Markdown's relative images always ask for `convert: "jpeg"`, the server converts only HEIC/HEIF). Transient answers (503 busy, 504, decode timeout) are not cached by path and get a "Try again" button. `system_manager.view_image` returns `(content, type, path, converted_from)`; a converted image has type `image/jpeg`, the same safe headers and `X-Motuz-Converted-From: image/heic`; the footer says "HEIC, converted to JPEG". **The conversion** (`utils/heic_convert.py` + `utils/heic_child.py`, `pi-heif` 1.4 + Pillow, pinned in `requirements.in`, installed from the hashed `requirements-heic.txt` with `--require-hashes`; the wheel bundles libheif and libde265, LGPL-3.0, decode only, no x265/GPL encoder) never runs in the server process: the bytes (read as the user, under the size cap) go on stdin of `sudo -n [--preserve-env=..] -u <owner> /usr/bin/env <MOTUZ_HEIC_PYTHON> -I -c <heic_child.py> <MOTUZ_HEIC_SITE>` (the existing sudo rule; `command()` refuses root, uid 0 and the account the server runs as) and the JPEG comes back on stdout, nothing is written to disk. The child sets RLIMIT_AS 2 GiB, CPU 60 s, FSIZE 0, NOFILE 64, CORE 0 before reading (each to the wanted value or the lower hard limit it was started with; if one cannot be set it exits `EXIT_LIMITS` and decodes nothing), refuses more than 100 megapixels from the header (413), decodes the primary image only (libheif applies irot/imir; leftover EXIF orientation via `exif_transpose`), caps the long side at 8192 px, writes JPEG quality 85 with no EXIF/XMP/GPS (only the ICC profile is kept), the parent reads at most 64 MiB of its stdout (stderr goes nowhere) and kills its process group after 60 s (504); at most `MOTUZ_HEIC_MAX_CONCURRENT` (default 2, 1..16, validated in `config.py`) conversions run at once, the others wait 5 s and get 503 "busy". Exit codes map to 415 (not decodable) / 413 (pixels, memory, SIGKILL = the OOM killer) / 503 (not installed) / 504 (CPU limit) / 500 (sudo/env/interpreter failures and unknown codes, logged with the exit code, never content). `MOTUZ_HEIC_PYTHON`/`MOTUZ_HEIC_SITE` default to the server's own interpreter and its packages (right for the Docker image: pi-heif and Pillow are also installed with `--target /opt/motuz-heic/site`, world-readable, `ENV` set in the Dockerfile, because `/root/.local` is not readable by users); the systemd install sets `/usr/bin/python3` and `/opt/motuz-heic/site` (`install.sh` runs `uv pip install --require-hashes --target` of `requirements-heic.txt` as root and records the file's hash, the Python tag and the architecture in `/opt/motuz-heic/STATE`; `deploy.sh` always sets both settings and warns loudly when pi-heif/Pillow do not import with them or STATE differs; `uninstall.sh --purge` removes the directory), since the service account's own Python is in its home. Other undecodable images show a generic message. **Previous/Next** (buttons, `←`/`→`, PageUp/PageDown; `utils/imageNeighbors.js`, node tests) step over the pane's image files in its displayed order (`state.pane.files[side]`, copied when the dialog opens, via `side`/`folder`/`index` added to the dialog's redux data by `apiActions.viewFile`), no wrap-around at the ends, showing "N / M"; the fit/100% choice is kept across a step, the pane's selection follows (`paneActions.fileFocusIndex`, the row looked up again by name with `rowIndexOf` since the pane may have been refreshed meanwhile, so closing leaves the cursor there), and a fetched image is cached by path (`this.cache`/`this.pending`) so stepping back is instant, pruned to just the current image and one preloaded next one (their `blob:` URLs revoked as soon as they fall outside that window) with a `loadSeq` token so a slow, now-stale fetch from fast stepping can never overwrite what is displayed. Markdown: up to `MARKDOWN_MAX_BYTES` (1 MiB) read with the chunk endpoint (notice + "Show the whole file as text" if larger), rendered by `MarkdownContent.jsx` (react-markdown 10 + remark-gfm, a lazy `import()` chunk of ~160 KB, never in the main bundle). No `rehype-raw`: raw HTML becomes text. `urlTransform`: `href` only http/https/mailto (`safeLinkUrl`, new tab, `rel="noopener noreferrer"`) or in-document `#fragments` (footnotes, scrolled in the container); other links render as `.md-link-disabled` text. Images: remote, protocol-relative and `data:` are never fetched (alt + "remote image not loaded"); relative/absolute paths are resolved against the file's folder (`markdownImageSource`) and, if an image extension (including HEIC/HEIF/AVIF), loaded through the image endpoint on the same connection (at most 50, 2 at a time, blob URLs revoked on close). "Rendered | Source" (`ViewerModeSwitch`, `setFileViewerMode` → `fileViewerDialogData.mode`) swaps to the pager (with follow) and back without the modal animation.

- **Document viewer (PDF, DOCX, XLSX/XLSM/XLSB/XLS/ODS, PPTX).** Everything renders in the browser; no LibreOffice, no server-side conversion, no external viewer service — a file never leaves Motuz. Double-click dispatches on `documentKind(name)` (`utils/viewerKind.js` `DOCUMENT_EXTENSIONS`; legacy `.doc`/`.ppt`/`.odt`/`.odp`/iWork/Keynote map to `'unsupported'`) to `DocumentViewerDialog.jsx`, whose four renderers (`PdfView`, `DocxView`, `SheetView`, `PptxView`) are separate lazy chunks (`viewer-pdf`/`viewer-docx`/`viewer-sheet`/`viewer-pptx`, loaded with the `viewer-document` chunk only on first use; the main bundle carries none of pdf.js, docx-preview, dompurify, fflate or SheetJS). `POST /api/system/files/view/document/ {connection_id, path[, offset, length]}` (`utils/document_view.py`, same reader/permission model as the pager and image endpoint: local `_VIEW_READER`, cloud `lsjson --stat` + `rclone cat`, 403/404/400/504, other users' connections 404) types the file from its first bytes only (`%PDF-`, `PK\x03\x04`, the OLE2 signature; never the name), and serves it two ways: DOCX/XLSX/PPTX/ODS/legacy files whole, refused above `MOTUZ_VIEW_DOCUMENT_MAX_BYTES` (default 50 MiB, 1K..512M, parsed at import like `VIEW_IMAGE_MAX_BYTES`; the e2e stack uses 4M) before and after reading; PDFs in ranges (`offset`/`length`, at most `RANGE_MAX_BYTES` = 4 MiB per request), so pdf.js opens a multi-GB PDF after a few small reads instead of loading it whole. Headers are the image endpoint's (nosniff, `Content-Security-Policy: default-src 'none'; sandbox`, no-store) plus `Content-Disposition: attachment` (the browser only fetches the bytes, never navigates to them) and `X-Motuz-Document-Type`/`-File-Size`/`-Range-Start`. The app's own pages carry a CSP too (`frontend_views.APP_CSP`: `img-src`/`font-src`/`connect-src 'self' blob: data:`, `media-src`/`worker-src 'self' blob:`, `frame-src`/`object-src 'none'`), so even a renderer bug cannot make the browser fetch anything from another site.

  - **PDF** (`pdfjs-dist` 6.3.289, the worker bundled by webpack from `node_modules`, never a CDN): one page at a time on a canvas plus a text layer (select, find with Ctrl+F, page by page with a progress notice) and link overlays; find, page navigation (arrows, typed page number, Home/End) and zoom (fit width, fit page, 25%-500% in steps) are keyboard- and toolbar-driven. Safety: PDF JavaScript is never run (no scripting sandbox loaded, `isEvalSupported: false`), XFA forms and form fields are off (`AnnotationMode.ENABLE` only draws appearances), and link annotations become clickable links only for a `dest` (internal, `doc.getDestination`/`getPageIndex`) or an http(s)/mailto `url` (`safeLinkUrl`, new tab, `rel="noopener noreferrer"`); Launch/JavaScript/remote-file actions are dropped. Fonts, cmaps and the WASM decoder are served from this build (`PdfjsAssetsPlugin` in `webpack.common.js`), never fetched externally.
  - **DOCX/DOTX** (`docx-preview` 0.4.1 into a detached DOM, then `dompurify` 3.4.16 with a hook (`DocxView.makeSanitizer`) before the nodes are attached inside a shadow root): `renderAltChunks: false` (an altChunk's embedded HTML is never rendered), macros (`word/vbaProject.bin`) are dropped by the document worker before docx-preview ever sees the ZIP, `href`/`xlink:href` are rewritten by `processLink` (bookmarks stay in-page links, http/https/mailto open in a new tab without opener/referrer, everything else — `javascript:`, `file:`, relative — loses its `href` and is shown struck through with "Link removed"), `src`/`srcset`/etc. are kept only for this page's own `blob:` URLs (docx-preview never fetches external pictures; a linked picture has no `src` and is greyed out with "not loaded"), and `url()` in style attributes/sheets is stripped (`utils/cssSafe.js`) except those same `blob:` URLs.
  - **XLSX/XLSM/XLSB/XLS/ODS** (SheetJS `xlsx` 0.20.3 from cdn.sheetjs.com — the npm registry copy is stale, CVE-2023-30533 — read with `cellFormula/cellHTML/cellStyles/bookVBA: false`): sheet tabs (hidden sheets marked, not shown by default), values only as the file formats them, formulas show their last cached value and are never evaluated, at most 5,000 rows × 200 columns × 200 sheets per workbook (`utils/sheetGrid.js` `SHEET_LIMITS`) with a notice ("first 5,000 of N rows") when a sheet or the workbook is cut off; only the cells scrolled into view are rendered (`visibleRange`).
  - **PPTX/PPTM/PPSX/POTX**: no maintained, safe browser PPTX renderer exists, so `utils/officeFiles.js pptxOutline` (a small hand-written OOXML walker, not docx-preview) extracts an outline instead of drawing slides — titles, text with list levels, tables, embedded PNG/JPEG/GIF/WebP pictures (by magic number; linked/external pictures and other media are listed as "not shown", never fetched) and speaker notes — shown as one card per slide with a slide list to jump to.
  - **Untrusted ZIP parsing** (`utils/zipSafe.js`, used by the document worker for every OOXML/ODF format): the central directory is checked against limits (`ZIP_LIMITS`: at most 10,000 entries, 200 MiB total and per-entry uncompressed, no encryption, only stored/deflate) before anything is inflated, and each entry is inflated in small steps into a buffer of its declared size, so a zip bomb with a lying central directory is stopped after at most one step; `rezip` rewrites the checked entries into a new, uncompressed ZIP that the renderers actually parse. The PPTX/`[Content_Types].xml` reader (`utils/officeFiles.js`) uses its own tiny, non-validating XML parser (`utils/xmlLite.js`): no DOCTYPE/entity definitions (refuses a DOCTYPE outright, so no billion-laughs), only the five predefined entities and numeric character references, and caps on node count and nesting depth. All of this runs inside a Web Worker (`workers/documentWorker.js`, one per document, terminated on answer, error or a timeout) so a hostile or huge file cannot freeze the page or leak into the next document; parsing errors and content mismatches (e.g. a PPTX named `.docx`) become a plain message, never a crash.
  - Legacy binary Office files (`.doc`, `.ppt`, `.pps`, `.pot`, `.dot`) and other formats without a browser renderer (`.odt`, `.odp`, `.pages`, `.numbers`, `.key`) show "No preview for this file type" without ever being read.
  - Fixtures for all of this are generated stdlib-only (`test/e2e/document_fixtures.py`: a hand-built PDF with link annotations and OpenAction JavaScript, a DOCX with a safe link/`javascript:` link/HYPERLINK field/bookmark/linked picture/altChunk, an XLSX with a hidden sheet and a cached formula, a PPTX with a table/linked picture/notes, zip bombs) and checked in `test/e2e/e2e_test.py`/`cred_test.py` (`common.check_document_view`) and the UI suite (`ui/ui_test.mjs`, screenshots of each viewer).
