# systemd install (default, without Docker)

Detail for the systemd install. Commands overview is in CLAUDE.md.

Default install, without Docker (Ubuntu 26.04 or Amazon Linux 2027, the default on EC2; `systemd --user` services of the account `motuz`; README "Install (default: without Docker)" with "Root steps without install.sh" (every root command by hand), "Install on Amazon Linux 2027 (default on EC2)"): `sudo bin/systemd/install.sh [--local-accounts] [--system-postgres|--private-postgres] [--system-redis|--private-redis]` once as root (Ubuntu defaults to the distribution's own PostgreSQL and Redis services, Amazon Linux to the private ones; an existing install keeps its mode, `bin/systemd/migrate_postgres.sh` moves private -> system with a row-count check), then as `motuz` `~/motuz/bin/systemd/deploy.sh [--pull]` on every update, or both in one step `sudo bin/systemd/bootstrap.sh --repo=URL --branch=B [install.sh options]` (EC2 user data: `deployment/aws/user-data-al2027.sh`); `bin/systemd/uninstall.sh [--purge --yes]`; `bin/systemd/migrate_from_docker.sh export|import` moves a docker install (the import goes into the configured database mode). `bin/systemd/config.sh show|set|ask-secret` edits `motuz.env`/`secrets.env` without printing secrets. An AI assistant can do the account's half: the playbook `.claude/skills/motuz-deploy/SKILL.md` (`/motuz-deploy`), guardrails `deployment/systemd/claude/settings.json` (copied to `~motuz/.claude/settings.json`: no sudo/su, no secrets files, no bypass mode), `bin/systemd/smoke_test.py` (README "Deploy with an AI assistant (Claude Code)"). Remote worker host: `install.sh --worker-only [--central-url=URL] [--pool=NAME] [--credential-file=FILE] [--run-as=NAME]` (writes `~/.config/motuz-worker/worker.env` with `MOTUZ_HOME` = the checkout it runs from, installs `motuz-worker.service`, starts it with a credential; `--run-as`: rclone only as that account, `MOTUZ_WORKER_RUN_AS`, like the EC2 workers); a temporary worker runs one job with `sudo bin/systemd/worker_once.sh --bootstrap-token-file=FILE` (transient user unit `motuz-worker-once`, exits with the worker's code). Tests: `test/e2e/run_systemd.sh [--distro=ubuntu|al2027] [--keep] [--reuse] [suite ...]` (`MOTUZ_E2E_INSTALL_OPTS` passes options to `install.sh`; a real Ubuntu 26.04 VM: `test/e2e/systemd/vm.sh`, QEMU/KVM in docker; or an AL2027 container with systemd as PID 1 and its own network namespace: `test/e2e/systemd/container.sh`; the same suites plus `security`), `test/e2e/systemd/worker_host_test.sh` (after `--distro=al2027 --keep`: a worker-only container sharing its network), `test/e2e/systemd/migration_test.sh` (docker e2e stack -> VM).

The systemd install (`bin/systemd/`, `deployment/systemd/`; the default install) runs the same pieces as user units of `motuz` (`deployment/systemd/user/`, copied to `~/.config/systemd/user` by `deploy.sh`, grouped by `motuz.target`, linger): and, in their **private** modes only, `motuz-postgres` (the distribution's PostgreSQL 18 binaries, cluster `~/data/pg`, 127.0.0.1:5432, socket in `%t/motuz-postgres`) and `motuz-redis` (Celery broker `MOTUZ_CELERY_BROKER_URL=redis+socket://:<MOTUZ_REDIS_PASSWORD>@/run/user/<uid>/motuz-redis/redis.sock`, no TCP; `~/.config/motuz/redis.conf` and `broker.env` generated; `CELERY_BROKER_TRANSPORT_OPTIONS` sets a 30-day `visibility_timeout` for Redis brokers, `MOTUZ_CELERY_VISIBILITY_TIMEOUT`), `motuz-app` (uWSGI from `~/motuz/venv`, `ExecStartPre=manage.py db upgrade`), `motuz-celery` (`KillMode=mixed`, `TimeoutStopSec=300`), `motuz-traefik` (the account's pinned `/var/lib/motuz-bin/traefik`; `TRAEFIK_ARGS` in `~/.config/motuz/traefik.env` is generated by `bin/systemd/traefik_args.py` from the traefik `command:` of `docker-compose.yml`, so change flags only there; `motuz.yml` reads the certificate directory from `MOTUZ_TRAEFIK_CERTS_DIR`, default `/certs`). **Where PostgreSQL and the broker live** (`MOTUZ_DATABASE_MODE` private|system|external, `MOTUZ_BROKER_MODE` private|system in `motuz.env`; `_lib.sh` `database_mode`/`broker_mode` infer them for older installs: host other than 127.0.0.1:5432 = external, `~/data/pg` = private, `~/.config/motuz/redis.conf` = private; install.sh `pick_mode` never switches an existing install silently): Ubuntu defaults to the distribution's services (`DEFAULT_POSTGRES`/`DEFAULT_REDIS` in the distro module), Amazon Linux to the private ones. `install.sh --system-postgres` (`bin/systemd/_system_services.sh`, `distro_system_postgres_prepare`: Ubuntu `pg_createcluster 18 main` + `postgresql@18-main`, AL `postgresql-setup --initdb` + `postgresql.service`): localhost only, role `motuz_user` (scram) + database `motuz` owned by it, `CONNECT` revoked from PUBLIC, `# BEGIN motuz` lines at the top of `pg_hba.conf` (scram on 127.0.0.1/::1, reject elsewhere). `--system-redis` (Ubuntu only; AL has no include directory in `valkey.conf`): `/etc/redis/motuz.conf` (`include` of the package's, `port 0`, socket `/run/redis/redis-server.sock` mode 770 group `redis`, `appendonly yes`, `user default off`, ACL user `motuz` with the SHA-256 of the password and `-@admin -@dangerous -@scripting +eval +evalsha +script|load`: kombu releases its lock with a script) selected by the drop-in `redis-server.service.d/motuz.conf`; `motuz` joins group `redis`; broker URL `redis+socket://motuz:<pw>@/run/redis/redis-server.sock`. Passwords reach the account through `/etc/motuz/handoff-<account>.env` (root:account, mode 640, written fresh by every `install.sh` run so it only holds the system modes; `deploy.sh` merges it into `motuz.env`/`secrets.env`; a pending private -> system PostgreSQL switch is only warned about until `migrate_postgres.sh`). **Root never writes, chowns or follows names inside the account's home** (it controls them: symlinks): the worker files are made with `account_mkdir/account_write/account_env_set` (`runuser -u <account>`), the account's files are read with `account_env_get`, and everything root takes from them is validated (`valid_secret` = 64 hex digits before it reaches psql or the Redis ACL line, `valid_port`). The sudoers rule excludes `postgres`, `redis` and `valkey` (they would own the system services). `install.sh` does not take over a system PostgreSQL/Redis that something else uses (other databases, non-localhost listen, keys/clients/auth/port in Redis) unless `--system-postgres`/`--system-redis` is explicit; the system PostgreSQL moves to 5433 (`distro_system_postgres_set_port`, `pg_conftool` on Ubuntu) while the private cluster holds 5432 and back with the next `install.sh`. `migrate_postgres.sh` refuses while jobs run (`--force`), restarts the app on failure and keeps `--rollback` data. `install_units` installs `motuz-postgres.service`/`motuz-redis.service` only in private mode and wires them with drop-ins (`motuz.target.d/10-*.conf`, `Requires=`/`Wants=` + `After=` in `motuz-app`/`motuz-celery`), so the units themselves name neither; system/external modes never start or require them. `uninstall.sh` never removes a system cluster or Redis (`--purge` drops only database `motuz`/role `motuz_user`, our `pg_hba.conf` lines, `/etc/redis/motuz.conf` and the drop-in). Settings `~/.config/motuz/motuz.env` (template `deployment/systemd/motuz.env.example`), secrets `secrets.env` (mode 600; systemd EnvironmentFile syntax, read in scripts with `env_get`, never `source`d). The venv's Python is the distribution's `/usr/bin/python3.14` (`DISTRO_PYTHON` in both distro modules; `python3-dev` builds uWSGI; deploy.sh recreates a venv of another version), or uv's `PYTHON_VERSION` 3.12 for a module without `DISTRO_PYTHON` (`deployment/systemd/versions.env` pins Traefik, uv and that Python; rclone comes from the app Dockerfile's `RCLONE_*` args). **rclone, Traefik and uv are the account's**: `install.sh` makes `/var/lib/motuz-bin` (`TOOLS_DIR` in `_lib.sh`, outside the home, which stays 750) owned by the account, and `bin/systemd/tools.sh` (run by `deploy.sh`, by `install.sh --worker-only` via `runuser` with `--rclone-only`) downloads them there SHA256 checked, so new pins need no root; the sudoers rule names `/var/lib/motuz-bin/rclone`, the app and celery units set `MOTUZ_RCLONE` to it (`rclone_connection.rclone_path` accepts only that or `/usr/local/bin/rclone`), worker.env too. Root never runs them (`test_root_never_runs_the_account_tools`): the HEIC converter is installed with a uv that `install.sh` downloads to its temporary directory. Older installs' `/usr/local/bin/{rclone,traefik,uv}` stay (install.sh says so); `uninstall.sh --purge` removes both. Everything distribution specific (packages, PostgreSQL/Redis paths as `@PG_BINDIR@`/`@REDIS_SERVER@` in the units, the PAM template `deployment/systemd/pam.d/motuz.<distro>`, `DISTRO_SERVICES` to mask, `DISTRO_PYTHON`, worker packages, firewall hint) is in `bin/systemd/distro/<ID>.sh`, selected from `/etc/os-release` (`test_systemd_support.TestDistroModules` checks the contract): `ubuntu.sh`, and `amzn.sh` for Amazon Linux 2027 (Valkey 9 as the broker, since AL2027 has no RabbitMQ or Redis; `postgresql18-server`; its Python 3.14, which passes the unit and e2e tests with the 3.12-compiled `requirements.txt`; `nodejs24`; PAM `password-auth`). Network tuning (also `--worker-only`, off with `--no-network-tuning`): `/etc/sysctl.d/61-motuz-network.conf` from `_lib.sh` `network_tuning_conf` (TCP buffers up to 128 MiB, BBR + fq if available, never lowers existing values), `tcp_bbr` in `/etc/modules-load.d/motuz-bbr.conf`; `uninstall.sh` removes both. SELinux (enforcing on AL2027) needs no booleans or modules: the user services run as `unconfined_u`, `install.sh` only runs `restorecon` on what it writes. Remote or multi-node workers are not part of it (they come with an HTTPS worker API).
